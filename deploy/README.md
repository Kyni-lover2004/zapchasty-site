# Сервер Ubuntu / Debian

Схема: Nginx → Gunicorn/Django → PostgreSQL. Фотографии: `/srv/z62/media`, вне базы. Изменения каталога видны после обновления страницы магазина. Заказы остаются в Telegram, автоматического списания остатков нет.

## Установка на новом сервере

1. Установить системные пакеты `python3-venv`, `python3-dev`, `postgresql`, `nginx`, `certbot`, `python3-certbot-nginx`.
2. Создать системного пользователя `z62`, каталог `/srv/z62`, скопировать туда проект **без `.local`, `admin-access.txt`, `.venv`, `media` и служебных файлов Mac**. Отдельно перенести фото, если нужно. Владельцем проекта сделать `z62`, группой `www-data`; фото должны читаться nginx.
3. В `/srv/z62`: `python3 -m venv .venv`, затем `.venv/bin/pip install -r requirements.txt`.
4. От имени администратора PostgreSQL создать роль: `sudo -u postgres createuser --pwprompt z62`, затем базу: `sudo -u postgres createdb --owner=z62 z62`. Рабочей роли не нужны права суперпользователя или создания баз.
5. Скопировать `deploy/env.example` в `/etc/z62.env`, заполнить домен, случайный секрет и пароль базы. Секрет можно получить командой `python3 -c 'import secrets; print(secrets.token_urlsafe(64))'`. Файл доступен только root и группе z62 (0640). PostgreSQL слушает только локальный адрес; порт базы не открывать наружу.
6. Под пользователем z62 загрузить переменные: `set -a; . /etc/z62.env; set +a`. Выполнить `.venv/bin/python backend/manage.py migrate`, затем `import_catalog`, затем `createsuperuser`. Импорт начального каталога запускается **один раз**, при наличии товаров он откажется перезаписывать их.
7. Выполнить `.venv/bin/python backend/manage.py collectstatic --noinput` и `.venv/bin/python backend/manage.py check --deploy`. Создать папку media, доступную для записи пользователю z62 и чтения nginx.
8. Установить `deploy/shop.service` в `/etc/systemd/system/z62.service`, выполнить `sudo systemctl daemon-reload` и `sudo systemctl enable --now z62`.
9. Настроить домен и TLS через Certbot. Адаптировать `deploy/nginx.conf` под свой домен и пути сертификатов. По умолчанию админка и склад доступны только с самого сервера. Для сотрудников через VPN добавить конкретные доверенные адреса в `allow` перед `deny all` и в `SHOP_STAFF_NETWORKS`. Проверить `nginx -t`, затем перезагрузить Nginx. Шаблон рассчитан на уже выпущенный сертификат.
10. На роутере/сервере открывать только необходимые порты 80/443; SSH ограничить доверенными адресами или VPN. Если провайдер использует CGNAT, потребуется публичный IP или отдельное решение доступа — простого проброса порта недостаточно.

Сервис не открывается наружу автоматически. Установка на будущий Xeon, TLS и резервное копирование проверяются отдельно на целевом сервере.

## Защита админки и склада

`/admin`, `/admin/` и все вложенные страницы, а также `/warehouse` и `/warehouse/` закрыты по адресам в Nginx и Django. Посторонний получает 404, включая страницу входа. Витрина и публичный каталог остаются доступными. Правило Django включено всегда; прежняя переменная `SHOP_LOCAL_ADMIN_ONLY` больше не используется. Не разрешайте всю домашнюю или офисную подсеть ради одного сотрудника.

В рабочем окружении обязательны `SHOP_DEBUG=0` и `SHOP_BEHIND_PROXY=1`. Nginx перезаписывает `X-Real-IP` и `X-Forwarded-Proto`, а Django принимает адрес клиента только от прокси из `SHOP_TRUSTED_PROXY_NETWORKS`. Не используйте присланный посетителем `X-Forwarded-For` для выдачи доступа. Без корректного адреса от доверенного прокси запрос отклоняется. Gunicorn должен слушать только `127.0.0.1`, как в `shop.service`; порт 8000 наружу не открывать. Если перед Nginx появится CDN или другой прокси, его доверие и адреса нужно настроить отдельно до включения доступа сотрудников.

Вход допускает пять POST-запросов с одного адреса за пять минут; шестой получает 429 и `Retry-After`. Учитываются все отправки формы, включая успешные и запросы без CSRF. Окно не продлевается заблокированными запросами. Счётчик хранится в PostgreSQL и общий для всех процессов, поэтому ограничение работает и при прямом запуске Django. Просмотр формы не расходует попытки. В базе сохраняются только хеш адреса, количество и срок действия; истёкшие записи удаляются при следующей отправке формы. Сотрудники за одним внешним IP делят лимит.

HTTPS, защищённые cookies и HSTS на один час включены при `SHOP_DEBUG=0`. HSTS не распространяется на поддомены, preload не включён: `check --deploy` выводит соответствующие предупреждения W005 и W021. Эти настройки можно включать только после проверки TLS на всех поддоменах и готовности к долгосрочному принудительному HTTPS. По HTTP служебные пути сразу возвращают 404; вход выполняется по HTTPS. Пароль администратора не изменён: перед открытием рабочего доступа сотрудникам замените временный пароль.

При обновлении существующей установки сначала выполните `.venv/bin/python backend/manage.py migrate` в окружении проекта (миграция `0016_login_attempt_window`), обновите переменные и конфигурацию Nginx, проверьте `nginx -t` и `.venv/bin/python backend/manage.py check --deploy`, затем перезапустите приложение и перезагрузите Nginx. Локальная миграция уже применена; рабочий сервер обновляется отдельно.

Проверьте с внешнего адреса, что `/admin/`, `/admin/login/`, `/warehouse/`, `/warehouse/stock/` возвращают 404, а `/` и `/api/catalog/` открываются. С разрешённого адреса форма входа должна открываться, а данные и операции по-прежнему требовать авторизацию и нужные права. Не проверяйте лимит на рабочем IP сотрудника в часы работы: тест временно исчерпает его попытки.

## Работа сотрудника

- Открыть `/admin/`, войти, выбрать «Товары».
- В списке можно менять цену, остаток, флаги публикации и главной страницы. После правок нажать «Сохранить» внизу списка.
- Нажать название для полной карточки. Характеристики — отдельными строками; совместимые модели — по одной на строку.
- В разделе «Фотографии» нажать «Выбрать файл». Для нескольких фото нажимать «Добавить ещё одну фотографию». Сохранить карточку. Допускаются JPG, PNG и WebP до 15 МБ и 25 мегапикселей; суммарно один запрос загрузки ограничен Nginx до 32 МБ.
- Главное фото — с наименьшим номером в поле «Порядок». Остальные доступны в галерее товара. Фото уменьшаются до 1600 px по длинной стороне, перекодируются в WebP, исходные метаданные удаляются.
- Для удаления связи фото отметить «Удалить» в соответствующей строке и сохранить. Старые файлы намеренно остаются на диске: автоматической необратимой очистки нет. Периодическую очистку неиспользуемых файлов выполняет администратор после резервного копирования.
- Для временного снятия товара убрать «Показывать на сайте». Сам товар не удаляется.
- Чтобы удалить товар, отметьте его галочкой и нажмите «Удалить» в строке. Откроется подтверждение. Кнопка доступна пользователям с правом удаления товаров.
- Создать каждому сотруднику отдельного пользователя с флагом «Статус персонала» и правами просмотра/добавления/изменения товаров, фото и характеристик. Не выдавать суперпользователя. Локально подготовлена группа «Редакторы каталога»; на сервере создайте её с теми же правами через раздел «Группы».

## Контакты и соцсети

В админке откройте «Настройки магазина» → «Контакты и соцсети» через ссылку с адресом. Здесь меняются адрес самовывоза, график, телефон и ссылки на Telegram и VK. Изменения видны после обновления витрины. Пустой телефон скрывается, пустая ссылка оставляет соцсеть недоступной. В Telegram указывайте HTTPS-ссылку на чат вида `https://t.me/имя`.

Доступ есть у суперпользователя. Чтобы делегировать его сотруднику, добавьте его группе права просмотра и изменения объекта «Контакты магазина» в разделе «Группы».

## Резервные копии

`deploy/backup.sh` создаёт дамп PostgreSQL, архив фотографий и `manifest.json` с размерами и SHA-256. Каталог помечается `.incomplete` до завершения всех операций. Скрипт отказывается писать копии внутрь проекта. Запускать с переменными PG*, SHOP_MEDIA_ROOT и абсолютным BACKUP_ROOT на **отдельном диске**. Скрипт сам по себе не устанавливает расписание. Для точного общего среза приостановить изменения в админке; во время копирования не запускать ручное удаление старых фотографий. Хранить также защищённую копию `/etc/z62.env` отдельно.

Подготовлены `shop-backup.service` и `shop-backup.timer`: ежедневный запуск в 03:00 по Москве с выполнением пропущенного запуска после включения машины. **Пока BACKUP_ROOT не выбран, таймер не устанавливать и не включать.** На сервере после выбора и монтирования диска заполнить BACKUP_ROOT, проверить права пользователя z62 на каталог, вручную выполнить `sh deploy/backup.sh`, проверить восстановление, затем скопировать оба unit-файла в `/etc/systemd/system/`, выполнить `systemctl daemon-reload` и `systemctl enable --now shop-backup.timer`. Убедиться в расписании через `systemctl list-timers shop-backup.timer`, журнал смотреть через `journalctl -u shop-backup.service`. Старые копии автоматически не удаляются: срок хранения и вместимость диска ещё нужно выбрать.

`sh deploy/verify-backup.sh /absolute/path/to/backup` проверяет контрольные суммы, читает архив фотографий и восстанавливает дамп в новую базу со случайным именем `z62_verify_…`. После проверки временная база удаляется. Рабочая база не изменяется. Нужны PostgreSQL CLI в PATH, PGHOST/PGPORT/PGUSER/PGPASSWORD и PGDATABASE для служебного соединения. Проверку выполнять отдельной ролью с правом CREATEDB; рабочей роли сайта это право выдавать не нужно. Проверку восстановления запускать после настройки копирования и регулярно вручную. На Mac сценарий проверен на реальном дампе и тестовом архиве; повреждённая копия отклоняется.

Восстановление: остановить приложение; создать пустую базу с нужным владельцем; выполнить `pg_restore --no-owner --dbname=z62 /path/catalog.dump` от роли z62; распаковать архив в media и восстановить владельца; запустить приложение. Сначала проверить восстановление на тестовой базе. Политика удаления старых копий выбирается владельцем сервера.

## Ошибки и доступность

Логи Django и мониторинга выводятся в stderr/stdout; unit приложения направляет их в journal. Просмотр: `journalctl -u z62.service -n 100` и `journalctl -u shop-monitor.service -n 100`. Пароли, содержимое корзины и персональные данные не добавляются в сообщения мониторинга.

`/health/` проверяет соединение с PostgreSQL и возвращает `{"status":"ok"}` или общий ответ 503 без причины сбоя. Команда `.venv/bin/python backend/manage.py check_site` проверяет SHOP_MONITOR_URL с тайм-аутом десять секунд и сохраняет переходы состояния. Подготовлены `shop-monitor.service` и `shop-monitor.timer` для проверки раз в минуту. На Mac они не включаются: сервер ещё не собран. На сервере задать реальный HTTPS-адрес в SHOP_MONITOR_URL, вручную проверить команду, затем установить оба unit-файла и включить `shop-monitor.timer`.

Telegram-уведомления отключены (`SHOP_ALERTS_ENABLED=0`). Это необязательные служебные сообщения владельцу о сбое и восстановлении, а не бот для заказов. Заказы покупателей остаются в личной переписке. Если уведомления понадобятся, заполнить SHOP_TELEGRAM_TOKEN и SHOP_TELEGRAM_CHAT_ID в защищённом `/etc/z62.env` и только затем включить SHOP_ALERTS_ENABLED. Первое успешное наблюдение не отправляет сообщение; повторяющийся сбой не дублируется. Отправка в Telegram сейчас не проверялась и не выполнялась. Проверка на самом сервере не сможет предупредить о полном выключении этой машины: для этого потребуется внешний мониторинг после выбора домена.

## Каталог и ссылки на товары

Стартовый `/api/catalog/` возвращает максимум 12 карточек, общие счётчики и контакты. Поиск `?mode=search` выполняется в PostgreSQL, выдаёт по 24 карточки и поддерживает q/cat/brand/model/stock/min/max/sort/page. Подбор моделей также разбит на страницы. Корзина и избранное загружают сохранённые карточки отдельными порциями; перед оформлением, копированием сообщения и переходом в чат корзина проверяется заново. Изменение цены, уменьшение остатка и снятие товара с публикации показываются покупателю. Резервирование не выполняется: сотрудник по-прежнему подтверждает заказ в переписке.

Карточки открываются по `/product/<slug>/`, содержат серверный текст без JavaScript, canonical и Open Graph. При наличии фото в превью используется оно, иначе — общая иллюстрация магазина. `/sitemap.xml` включает только опубликованные товары; `/robots.txt` исключает служебные пути и API. На рабочем сервере обязательно заполнить SHOP_PUBLIC_URL реальным HTTPS-доменом. Индексация и внешние превью проверяются после публикации, локальный IP для поисковых систем недоступен.

## Локальная проверка на текущем Mac

Подготовлены отдельная PostgreSQL в `.local/postgres` (порт 55462), окружение `.local/env` и учётная запись в `.local/admin-access.txt`. Не переносить эти секреты на рабочий сервер.

Из корня проекта: `source .local/env`, затем `.venv/bin/python backend/manage.py runserver 127.0.0.1:8000 --noreload`.

В локальном окружении установлены `SHOP_BEHIND_PROXY=0` и пустой `SHOP_STAFF_NETWORKS`; доступ всей сети `192.168.1.0/24` удалён. `SHOP_DEBUG=1` остаётся только для разработки: middleware отклоняет любые нелокальные запросы, включая витрину, до вывода отладочных страниц. Для публикации используйте рабочую схему с Nginx и TLS выше.

При остановленной базе: `/opt/homebrew/opt/postgresql@16/bin/pg_ctl -D .local/postgres -l .local/postgres.log start`.

Тесты: `.venv/bin/python backend/manage.py test shop` (локальная роль может создавать тестовую базу), `node --test tests/catalog.test.cjs`.

Для просмотра с устройств домашней сети запустить второй процесс `.venv/bin/python .local/lan_preview.py --host <IP_этого_Mac>` при работающем Django на 127.0.0.1:8000. Витрина слушает тот же порт на указанном сетевом адресе и пропускает только публичные страницы, файлы каталога и health. Админка, склад, POST-запросы и отладочные ответы через неё недоступны. Скрипт в `.local` не переносить на рабочий сервер.
